# 电商自动化生图中台设计规格

- 日期：2026-08-17
- 状态：产品与架构设计已确认；M0–M3 已实施，M4–M5 待分阶段实施
- 目标读者：产品、设计、前端、后端、算法、测试和运维人员

## 1. 背景

项目需要建设一套面向国内外主流电商平台的自动化生图中台。系统以商品/SKU为核心，接收一张或多张商品参考图及结构化商品资料，生成不同平台所需的商品主图、辅图、场景图、详情图和服装鞋帽专项图片。

服装鞋帽专项需要同时支持系统虚拟模特和用户上传的真人/指定模特，覆盖商品图、模特图、多角度图片和虚拟试穿。运营人员可以在后台配置生图模型API Key、选择模型和模板、批量生成图片、审核结果，并对任意单图进行局部编辑。

系统不是通用生图社区，也不是ComfyUI换皮。核心价值是商品真实性、平台规则、批量生产、人工审核、资产追溯和可控编辑。

## 2. 产品目标

1. 将“上传商品素材到平台可用图片”的流程收敛为可重复、可审核的自动化工作流。
2. 通过平台规则包、商品品类包和品牌视觉包生成可复用的图片套装。
3. 通过统一模型适配层连接商业API、OpenAI-compatible接口和本地ComfyUI执行节点。
4. 保留每张图片的输入、模型、参数、模板、成本、版本和审核记录。
5. 让运营人员无需理解节点图即可使用复杂的图片生成与编辑能力。
6. 默认保护商品真实性，不把模型推测出的商品结构伪装成真实拍摄结果。

## 3. 非目标

首版不包含以下能力：

- Photoshop级完整编辑器、钢笔路径、高级滤镜和CMYK印刷工作流。
- 自研基础生图模型或完整的模型训练平台。
- 自动发布商品到所有电商平台。
- ERP、PIM、DAM等企业系统的全量替代。
- 面向公众的模型社区、作品广场或提示词交易市场。
- 自动生成未经用户确认的商品参数、功效和促销承诺。

## 4. 用户与权限

首版包含四类角色：

- 管理员：管理用户、模型、API Key、平台规则、系统配置和审计记录。
- 运营：管理SKU、素材、模板、生成任务和导出批次。
- 设计：管理品牌视觉包、编辑单图和处理驳回结果。
- 审核：查看质检证据，通过或驳回图片，不能修改模型密钥。

一个用户可以同时拥有多个角色。权限由后端校验，前端隐藏按钮不视为安全边界。

## 5. 核心概念

### 5.1 商品与真实性锚点

每个SKU包含结构化资料、原始参考素材和真实性锚点。真实性锚点至少覆盖：

- 款式轮廓、主色、辅色和材质纹理。
- Logo、图案、包装文字、型号和规格数字。
- 服装的领型、袖型、口袋、纽扣、拉链和下摆。
- 鞋类的鞋底、鞋面、鞋带、鞋跟和装饰件。
- 帽类的帽檐、帽冠、织物结构和装饰件。
- 用户手工圈选的绝对不可修改区域。

锚点来源于商品资料、自动分析和人工修订。后续所有工作流引用同一份带版本的锚点快照。

### 5.2 三层模板

图片生产模板由三层组合：

```text
平台规则包 × 商品品类包 × 品牌视觉包 = 图片套装计划
```

- 平台规则包：站点、市场、尺寸、比例、背景、主体占比、文字限制、文件格式和导出命名。
- 商品品类包：图片用途、视角、特写、模特姿势、场景和质检重点。
- 品牌视觉包：字体、色板、Logo安全区、摄影风格、文案语气和禁用元素。

三个规则包均使用不可变版本。生成任务保存实际使用的版本号，规则升级不改变历史结果。

### 5.3 模特资产

模特分为系统虚拟模特和品牌指定模特。模特资产包含：

- 性别、年龄段、体型、肤色、发型和地区风格等结构化标签。
- 全身、半身、正面、侧面和背面参考图。
- 允许使用的商品品类、平台和品牌。
- 肖像授权状态、有效期和内部备注。
- 默认姿势、背景、摄影风格和身份一致性参考集。

首版通过多参考图和模型适配器保持身份，不建设LoRA训练平台。

## 6. 真实性模式

### 6.1 严格商品模式

严格商品模式是默认模式，适合商品主图、详情图和正式上架素材。

- 缺少背面、侧面或内部结构参考时，不生成并导出相应真实商品视角。
- 商品结构、Logo、图案、包装文字和关键颜色漂移时，自动质检必须拦截。
- 未通过人工真实性审核的图片不能进入可导出状态。
- 不允许模型自行补充商品参数、材质、功效或促销信息。

### 6.2 创意模式

创意模式适合广告创意和内部概念图。

- 允许模型推测被遮挡区域或缺失视角。
- 结果在中台内部标记为“AI补全待审核”。
- 创意模式结果不能混入严格模式的导出批次，除非审核人明确转换并记录原因。

## 7. 核心业务流程

```text
创建/导入SKU
  → 上传并分类参考素材
  → 自动分析并人工修订真实性锚点
  → 选择平台、市场、语言、模板和模特
  → 编译图片套装生产计划
  → 运营人员增删或调整单图任务
  → 批量生成
  → 自动质检
  → 人工审核
  → 必要时单图编辑或重新生成
  → 编辑后重新质检和审核
  → 按平台规则导出
```

每张图片是独立的资产版本和任务输出。单张失败、编辑或重试不要求整套图片重新执行。

## 8. 功能范围

### 8.1 工作台

- 今日任务、排队任务、失败任务和待审核图片。
- 模型调用次数、成功率、耗时和费用。
- 最近商品、生成批次、异常任务和快速重试入口。

### 8.2 商品中心

- 创建、编辑、归档SKU。
- 单个上传和Excel/CSV批量导入。
- 管理商品资料、原始素材、真实性锚点和品牌归属。
- 查看全部生成批次、编辑分支、审核和导出历史。

### 8.3 模特中心

- 管理系统模特与品牌模特。
- 上传多视角参考图并设置结构化标签。
- 管理授权状态、适用范围和身份参考集。

### 8.4 模板中心

- 管理平台规则包、商品品类包和品牌视觉包。
- 预览三层模板组合后的图片套装。
- 版本发布后保持不可变；修改生成新版本。

### 8.5 生图工作台

- 选择SKU、平台、市场、语言、模板和模特。
- 查看并调整系统编译的生产计划。
- 为单图指定模型、比例、参考素材和可覆盖参数。
- 批量执行，以瀑布流查看状态和结果。
- 通过、驳回、对比、单张重试、复制参数重做和创建分支。

### 8.6 单图编辑器

首版支持：

- 自动选择商品、人物、服装或背景。
- 画笔、擦除、反选、蒙版膨胀和羽化。
- 局部替换、消除、换背景和扩图。
- 商品移动、缩放、旋转、裁切和背景虚化。
- Logo、标题、卖点、参数和价格的独立图层。
- 图层顺序、锁定、隐藏、复制和透明度。
- 撤销、重做、版本快照和前后对比。

文字内容默认通过确定性图层排版完成。生图模型负责生成无字底图或装饰性场景文字，不负责最终商品规格和价格文字。

### 8.7 审核与导出

- 展示自动质检结论、风险等级和证据。
- 并排对比原始参考图、上一个版本和当前结果。
- 使用标准驳回标签并支持补充说明。
- 按平台输出目录、文件名、图片清单和审核记录。
- 保存导出批次，不覆盖历史导出。

## 9. 平台覆盖策略

平台能力通过规则包扩展，不在业务代码中硬编码。

第一批规则包：

- 淘宝/天猫。
- Amazon。
- TikTok Shop。

后续规则包：

- 京东、拼多多和抖音电商。
- Shopify、Temu、Shopee、Lazada和eBay。

平台规则必须保存来源、适用站点、生效日期和版本。规则更新通过新版本发布，历史任务继续使用原版本。

## 10. 系统架构

采用模块化单体加独立Worker的架构：

```text
Next.js运营后台 / 单图编辑器
              ↓
       FastAPI业务API
              ↓
  ┌───────────┼───────────┐
商品与模板   生成编排     资产与审核
  │            │             │
PostgreSQL  Redis任务队列   S3/MinIO
               ↓
        Python Worker集群
               ↓
  ┌────────────┼─────────────┐
商业模型API  ComfyUI节点   图像处理组件
```

### 10.1 技术选型

- 前端：Next.js、React和TypeScript。
- UI：项目内统一组件库；视觉方案在实施计划中按产品后台场景落地。
- 编辑画布：React Konva。
- 后端：FastAPI和Python。
- 数据库：PostgreSQL。
- 文件存储：开发环境MinIO，生产环境使用S3兼容对象存储。
- 队列：Redis负责唤醒和分发，PostgreSQL保存权威任务状态。
- 部署：Docker Compose起步，保持迁移至Kubernetes的容器边界。

### 10.2 后端模块

- Identity：用户、角色和权限。
- Catalog：SKU、商品资料、真实性锚点和参考素材。
- Model：模型Provider、能力、密钥和路由策略。
- Template：平台、品类、品牌规则及其版本。
- Workflow：生产计划编译、任务状态机和重试策略。
- Asset：对象存储元数据、版本关系、哈希和衍生关系。
- Review：自动质检、人工审核和驳回记录。
- Export：平台目录、命名、清单和导出批次。
- Audit：敏感操作、配置变更和关键业务事件。

这些模块在同一后端进程内通过显式服务接口协作，禁止跨模块直接修改数据表。

## 11. 模型适配层

业务工作流请求模型能力，不直接引用具体供应商SDK。统一能力集合为：

- `text_to_image`
- `reference_to_image`
- `multi_reference_to_image`
- `inpaint`
- `outpaint`
- `virtual_try_on`
- `remove_background`
- `segment`
- `upscale`
- `vision_analyze`
- `quality_inspect`

每个模型配置记录：

- Provider、模型标识、Base URL和启用状态。
- 能力、支持尺寸、比例、最大参考图数量和输出格式。
- 超时、并发上限、重试策略和回调方式。
- 计费单位、估算单价和适用品类。
- 严格模式可用性和备用模型优先级。

首批适配器：

- OpenAI-compatible图片接口。
- Google Gemini/Imagen。
- Replicate。
- ComfyUI HTTP/WebSocket。
- 通用HTTP/Webhook。
- Mock Provider。

ComfyUI是可选执行节点，不承担商品、模板、权限、审核和资产等中台业务职责。

## 12. 模型密钥安全

- API Key由服务端使用AES-GCM加密，主密钥来自服务端秘密管理或运行环境。
- 数据库仅保存密文、随机Nonce、Provider和显示用后缀。
- 前端不能读取已保存的完整Key，只能覆盖或轮换。
- 连接测试在服务端执行，响应必须脱敏。
- 日志、错误、任务输入快照和工作流文件不得包含完整Key。
- 密钥的创建、测试、轮换、启停和删除写入审计日志。

## 13. 任务模型与状态机

一个生成批次包含多个图片任务，一个图片任务包含多个可恢复步骤。

批次状态：

```text
DRAFT → READY → QUEUED → RUNNING → QA_PENDING → REVIEW_PENDING
                                                   ├→ APPROVED → EXPORTED
                                                   └→ REJECTED
```

任何执行状态都可以进入`FAILED`或`CANCELED`。失败任务在满足策略时进入`RETRY_QUEUED`，然后返回`QUEUED`。

每个执行步骤保存：

- 幂等键。
- 输入素材和输入哈希。
- 模板与真实性锚点快照。
- Provider、模型和参数。
- 请求标识、回调标识和供应商原始状态。
- 开始时间、完成时间、耗时和费用。
- 输出资产、错误分类和重试次数。

Worker使用租约领取步骤。租约过期后，扫描器先查询Provider状态，再决定恢复、重试或失败，避免重复计费。

## 14. 资产和版本

原始素材、模型输出、编辑结果、缩略图、蒙版和导出文件均作为资产保存。

- 资产内容按哈希去重，但业务记录保持独立。
- 每个衍生资产记录父资产、操作类型和参数。
- 编辑创建新版本，不覆盖父版本。
- 删除业务记录默认采用软删除；对象清理由异步保留策略完成。
- 已进入审核或导出记录的资产不能被物理覆盖。

## 15. 自动质检

自动质检分为五层：

1. 文件质检：尺寸、比例、格式、色彩空间、文件体积、模糊和压缩伪影。
2. 平台质检：白底、主体占比、安全边距、禁止文字、水印、边框、模块尺寸和数量。
3. 商品一致性：颜色、轮廓、Logo、图案、包装文字、规格数字和关键结构。
4. 服装模特：人脸、手指、四肢、人体边界、穿透、衣服结构和跨视角一致性。
5. 内容风险：敏感内容、商标风险、禁用元素、未经确认的参数和促销文字。

技术规则可以自动拦截。视觉一致性结果默认进入人工审核，不允许系统静默修改后直接通过。人工覆盖必须保存审核人、时间和原因。

## 16. 异常处理

- 限流和临时网络错误：指数退避并限制最大重试次数。
- 超时或回调丢失：先查询Provider状态，再决定恢复或重试。
- 余额不足或Key无效：禁用对应配置并通知管理员，不重复请求。
- 内容审核拒绝：保留原因，不自动重复相同请求。
- 空图片或格式错误：有限重试后按管理员配置切换备用模型。
- 商品一致性失败：保留失败结果，要求补充参考图、调整参数或换模型。
- Worker或Redis重启：从PostgreSQL恢复权威状态，任务不能因队列丢失而消失。

自动降级仅在管理员配置了同能力备用模型且不降低严格模式要求时执行。每次切换记录实际Provider、模型和费用。

## 17. 可观测性与成本

- 任务、步骤和Provider请求使用统一关联ID。
- 记录调用次数、成功率、P50/P95耗时、重试率和失败分类。
- 按Provider、模型、用户、SKU、批次和平台统计估算与实际费用。
- 对队列积压、连续失败、回调延迟和密钥失效建立告警。
- 普通日志不得记录原图二进制、完整提示词中的敏感资料或完整API Key。

## 18. 测试策略

- 单元测试：状态机、费用计算、模板编译、权限、脱敏和导出命名。
- Provider契约测试：所有适配器运行同一套能力输入输出规范。
- 图片固定测试集：验证抠图、OCR、尺寸、合成和质检。
- 快照测试：平台模板编译结果和导出目录结构。
- 集成测试：使用Mock Provider覆盖生成、回调、重试、审核和导出。
- 真实模型冒烟测试：使用专用测试账号按需运行，不进入默认测试套件。
- 前端端到端测试：SKU创建、套图生成、单图编辑、审核和导出。
- 安全测试：浏览器响应、日志、错误和任务记录中不存在完整API Key。
- 恢复测试：Worker中断、重复回调、Redis重启和租约过期时任务不丢失。

## 19. 分阶段交付

本文件是系统主规格，不把M0至M5合并成一次代码实施。每个里程碑使用独立实施计划、功能分支和验收记录。书面规格通过后的第一份实施计划只覆盖M0和M1：先完成模型能力验证框架，再交付可运行的基础中台纵切片。M2至M5在前一里程碑通过后分别制定实施计划，避免在基础边界未经运行验证时同时铺开全部平台和编辑能力。

### M0：模型能力验证

建立30个SKU基准集，服装、鞋、帽各10个，覆盖纯色、复杂花纹、Logo、文字、反光材质和遮挡情况。评估商品保持、系统模特、指定模特、虚拟试穿、多角度、局部编辑、中文文字、耗时和费用，形成模型能力矩阵。

### M1：基础中台闭环

完成用户权限、商品、素材、模型配置、任务编排、资产版本、审核和导出。使用Mock Provider和至少一个真实Provider跑通：

```text
创建SKU → 上传 → 生成 → 审核 → 单张重试 → 导出
```

### M2：商品主图和详情图

完成淘宝/天猫、Amazon和TikTok Shop第一批平台规则包，以及服装品类包、品牌视觉包、确定性文字图层和基础自动质检。

### M3：服装鞋帽专项

完成系统模特、指定模特、虚拟试穿、多角度、细节图和严格商品模式。服装、鞋、帽使用独立工作流和质检规则。

## 20. 发布门槛

在M0基准集上满足：

- 任务、回调、资产和审核记录不丢失。
- 相同输入和参数可以追溯并重新执行。
- 主图经最多一次重试后，平台技术规则通过率不低于90%。
- 虚拟试穿经最多两次生成后，人工真实性审核通过率不低于80%。
- 严格模式缺少背面或侧面参考时，不生成并导出对应真实商品视角。
- 完整API Key不出现在浏览器、普通日志和任务记录中。
- 导出图片可追溯到SKU、素材、规则版本、模型、参数和审核人。

如果候选模型达不到真实性门槛，应更换模型或增加参考图，不通过降低质检标准完成发布。

## 22. 已确认的关键决策

- 产品同时覆盖国内外主流电商平台和服装鞋帽专项。
- 同时支持系统虚拟模特和用户上传的真人/指定模特。
- 默认采用严格商品模式，创意模式单独标记和审核。
- 使用平台规则包、商品品类包和品牌视觉包组合图片套装。
- 采用Next.js、FastAPI、PostgreSQL、Redis、MinIO/S3和Python Worker。
- ComfyUI作为可选执行节点，不作为中台业务主干。
- 商品规格和促销文字使用确定性图层排版。
- 所有图片、模型调用和人工修改均保留版本与审计记录。
